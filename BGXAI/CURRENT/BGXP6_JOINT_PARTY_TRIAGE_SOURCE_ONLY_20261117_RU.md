## Ключевой технический барьер
Проверенный источник правды: EEex 1.1.7 не позволяет вывести **ручное происхождение действия и действительно пустую очередь EPS** только из `m_curAction.m_actionID=0`. 082 намеренно возвращает HOLD, поэтому `BGXP6` пока лишь проверенный координатор. Для полноценного автономного применения необходимо отдельно подтвердить runtime queue/origin и написать строгий мост к BCS/EEex с живым preflight, WeiDU backup и явным разрешением на установку. Не объявлять BGXP6 рабочим установленным ботом.

## Далее без повторения старых боёв
1. Разработка компактного **read-only** EEex наблюдателя для точных сведений о очереди, происхождении приказа и свежести подтверждённой атаки. Выводить UNKNOWN, если наблюдение недоступно, а не выдумывать флаги.
2. Подтверждение реального контракта API и корректности тик/идентичности на EET.
3. Только после доказательств — отдельный мост для действий, с сохранением работающего BGXP5 и ручных приказов, guarded WeiDU через тот же CMD.

**Правило:** пользователь просит продолжать безопасную разработку без ожидания согласований, но изменения живой EET — только после preflight и отдельного typed opt-in.
