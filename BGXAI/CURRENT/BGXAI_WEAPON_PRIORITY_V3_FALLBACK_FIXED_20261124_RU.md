# BGXAI — исправление реальных логических блокировок приоритетного оружия V3

**Дата:** 24.11.2026. **Фокус:** продолжение утверждённого выбора эффективного оружия, **не** повторная установка V6/V7. **CODE/TEST:** ниже. **DEPLOY/LIVE:** НЕТ. Исходники игры, ESP/EPS, сохранения, WeiDU, BG Voice RU, BG_EET_RU и один `BGXAI_UPDATE.cmd` не изменялись.

## Что исправлено в уже существующем V3

В `BGXAI_WEAPON_PRIORITY_LUA_V3.lua` ранее были две ошибки, препятствующие нормальной работе даже при полном подтверждённом снимке боевой ситуации:

1. `ammoCount=0` при `ammoVerified=true` давал глобальный `HOLD_AMMO_OR_THROWABLE_UNVERIFIED`, хотя достоверно пустой колчан означает **известную непригодность именно этого кандидата**. Теперь такой кандидат исключается с `VERIFIED_EMPTY_AMMUNITION`. Если выбранное оружие пустое, а другое доказанно полезно и безопасно, результат после стабильных двух наблюдений — **только совет** `ADVISE_PRIORITY_QUICKSLOT_ONLY`, с `currentUnusableReason` и **нулём игровых команд**. Если подходящих кандидатов нет или их доказанная полезность неположительная — `HOLD_NO_EFFECTIVE_ATTACK`.
2. Ранее один недостижимый/опасный ближний слот или дальнее оружие за пределами эффективной дистанции давали глобальный `HOLD_UNRANKABLE_OCCUPIED_WEAPON`. Теперь кандидаты с **доказанной** недостижимостью/опасностью исключаются отдельными причинами `VERIFIED_NO_SAFE_MELEE_PATH`, `VERIFIED_UNSAFE_TO_TANK`, `VERIFIED_RANGED_OUT_OF_RANGE`. Из оставшихся можно выбрать лучший безопасный вариант. **Неизвестная** безопасность пути, дальность, боеприпасы или численные параметры по-прежнему приводят к `HOLD`; неизвестность не превращается в разрешение.

Принципиально сохранено: `M.choose` блокируется при ручном/EPS приказе/лечении/касте; `M.preview` допускает только вычисление **без команды**; гистерезис из двух снимков и cooldown; порог выгоды для пригодного текущего оружия; никакого движения, переключения, `SetGlobal` или сброса очереди из Lua. Возврат чистого планировщика всегда `ordersSent=0` и `dispatchAuthorized=false`.

## Проверки

Реальные исходники V3/V4/APR V5 и существующий NONINTERRUPT протестированы вместе в Lua 5.3-совместимом интерпретаторе, с новыми регрессиями:

| Набор | Результат |
|---|---:|
| Приоритет V3, включая пустой колчан, опасный путь, хрупкого бойца и неизвестный EPS | 36/36 |
| Эффекты V4 | 30/30 |
| APR/proficiency V5, включая переход с пустых дротиков на пращу | 18/18 |
| Планировщик без прерывания | 22/22 |
| Сквозные V3+V4+active-stats+NONINTERRUPT, включая EPS/manual busy | 4/4 |
| **Всего поведения (оффлайн)** | **110/110 PASS** |

Независимая CI проверяет Lua 5.3 на Ubuntu и статическую невозможность команд V3 на Windows. **Это не боевой LIVE-тест и не доказательство отсутствующей EEex/EPS provenance.** Нельзя выдавать виртуальные `COMPLETE_EFFECTIVE_SNAPSHOT`, `allActiveEffectsObserved=true`, `provenEpsFree=true` за реальные поля игры.

## Следующая реальная точка, без диагностической спирали

Код поведения для отсутствующих боеприпасов и опасного сближения **теперь существует в основном V3**, а не в новом конкурирующем модуле. Осталось связать уже установленные R27 (LIVE callbacks 24/24) и R28 (фактические ITM/SPL/2DA) с **текущими эффективными характеристиками каждого кандидата**, подтверждённой парой launcher/ammo и достоверным приоритетом ручной команды/EPS в движке. Пока ни R27, ни R28 не дают всех этих фактов. Следующий игровой шаг должен быть конкретным ограниченным **исполнительным** модулем `SelectWeaponAbility(SLOT_WEAPON0..3,0)` из уже написанного `BGXAI_WEAPON_SLOT_CONSUMER_V3.baf`, с проверенным producer, native WeiDU, SHA/backup/last-only rollback и отдельным разрешением на изменение игры.

**Что делать пользователю сейчас:** ничего, нет новой установки. Не запускать 166→2 (дубликат V6), 165→5/6, 158/159 или другие старые проверки. Результат CODE/TEST следует считать только улучшением **алгоритма**, не внедрённой новой способностью партии.
