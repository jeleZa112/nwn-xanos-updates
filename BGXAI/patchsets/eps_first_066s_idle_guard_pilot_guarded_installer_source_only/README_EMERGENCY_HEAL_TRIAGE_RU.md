# BGXAI — экстренная сортировка раненых союзников после подтверждённого попадания

**Статус:** SOURCE ONLY; **не установлен в EET**. 16 ноября 2026. Это новый игровой алгоритм, не исправление установщика.

## Наблюдаемое поведение, которое должна дать функция

При подтверждённом EEex попадании в союзника вызов существующей `BGX66Caster.onHit()`:

1. В пределах **той же загруженной игровой области** проверяет текущее здоровье шести портретных персонажей (только достоверные `m_hitPoints` / `m_nMaxHitPoints`, положительные и корректные); учитывает текущий `S.victims` lease и допустимую позицию цели.
2. Если существует союзник с **HP <=20%**, которого ещё не обслуживает текущая краткая Lua-аренда, направляет запрос лечения **самому тяжелораненому**. Если здоровье одинаково критическое, сохраняет приоритет за **непосредственно атакованным союзником**; при разных критических союзниках сравнивает оставшиеся проценты здоровья и, при равенстве, оставляет первого подходящего в порядке портретов.
3. Если ни один союзник не критический, сохраняет прежнее поведение: запрашивает лечение текущего пострадавшего, только если его HP <45%. Если ни одна пригодная цель не найдена, не пишет запрос.
4. Сохраняет выбор потенциально свободного F-включённого лекаря по EEex `m_curAction.m_actionID==0` только как подсказке; при равных подсказках предпочитает ближайшего уже к **выбранной цели лечения**. `0` не доказывает пустую очередь EPS или отсутствие ручного приказа.
5. Выдаёт существующую BCS-заявку `BGX66_S_HEAL_SLOT` для **реального слота выбранного пациента**, а не слота атакованного. Для тяжелого пострадавшего мага сохраняет отдельную BCS-заявку `WIZARD_SHIELD` на самом атакованном маге. Одновременные запросы одному актёру ограничиваются прежней проверкой.
6. Ставятся короткие раздельные Lua-аренды только для реально подготовленных лечебных/защитных заявок. В диагностике есть `victim_id`, `heal_target_id`, `heal_target_percent`, `triage_redirected`, `healer_id`.

**Пример:** Ксар получает удар, имея 40% HP. У Имоуэн остаётся 7% HP. Новый кандидат направляет существующий запрос лечения на Имоуэн; охрана продолжает защищать Ксара. При отсутствии раненого <=20% алгоритм по-прежнему выбирает Ксара (<45%).

## Ограничения безопасности

- Никаких прямых `Spell`, `Attack`, `ClearActions`, `ProtectObject`, новых EEex-хуков, файловых операций и переписывания BCS/EPS/WeiDU. Только Lua-запросы существующему получателю BCS. Он **всё равно обязан проверить** `ActionListEmpty()`, F ON, `ModalState(NONE)`, `HaveSpell`, `HPPercentLT`, `See` и `Range(...,10)`.
- Критический союзник далеко от лекаря может **не получить** лечение: BCS не выполнит действие вне видимости/радиуса. В данной версии нет доказанного игрового LOS/Range API и нельзя утверждать, что лечение начато, лишь по готовности Lua-заявки.
- Не поддерживаются дополнительные лечебные заклинания и способность лечить всеми китами/дуалами: используются ранее установленные узкие условия класса и `CLERIC_CURE_LIGHT_WOUNDS`. Это ещё НЕ полноценный автономный AI.
- Никаких изменений рабочей игры `C:\Games\BG_EET_FOXX_NEW` и активного однофайлового автообновлятора. Нельзя запускать экспериментальную установку без отдельного согласия и внешней SHA-проверенной резервной копии.

## Что проверено

- **RED до изменения**: предыдущая версия Lua выбирала пострадавшего с HP 40%, даже когда в партии был союзник с HP 7%.
- **GREEN после изменения**: выбирается более тяжёлый пациент; охранник по-прежнему получает исходный объект защиты. Протестированы нормальный/критический HP, цель в другой ARE, неизвестные HP/координаты, F OFF, modal, уже активная заявка, раздельный mage Shield, два критических одинаковой тяжести, временные аренды/откат игрового времени и отсутствие прямых команд.
- Native Lua 5.4 + mock EEex: **18 baseline + 17 caster + 14 guard + 14 idle healer + 21 triage = 84/84 PASS**. Синтаксис через texlua PASS. Это **не проверка установленного движка игры и не реальный бой**.
- Новая реализация `M_BX43_066S_IDLE_GUARD_HEAL_TRIAGE_SOURCE_ONLY.lua`, тест `test_emergency_triage_source_only.py`; запуск набора `python run_triage_full_tests.py` в изолированной офлайн среде разработчика.

## Следующая настоящая игровая граница

1. Не тратить ход на ещё один установщик. Интеграцию делать только с текущим `BGXAI_UPDATE.cmd` и отдельно согласованным guarded WeiDU обновлением в установленной EET.
2. При разрешённом игровом A/B испытать ситуацию «попали по союзнику HP 40%, другой HP 7%, лекарь F ON свободен»; проверить фактическое использование лечения, `See/Range(10)`, отсутствие вмешательства в EPS/ручные приказы, реакцию охраны и точный WeiDU откат.
3. Невыполненное: общий командный планировщик, доказательство реальной доступности spell/kit, очередь действий и управление несколькими лекарями при одновременных угрозах.
