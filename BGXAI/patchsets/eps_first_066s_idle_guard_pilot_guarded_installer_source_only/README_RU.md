# BGXAI — узкая пробная правка действующей 066S: выбор свободного охранника

**Только исходники для согласованного игрового испытания. НЕ УСТАНОВЩИК. Установленная 066S, EPS 18.4 и все BCS должны оставаться неизменными, пока пользователь отдельно не разрешит испытание.**

## Обнаруженный механизм

По IESDP для BG(2)EE `ActionListEmpty()` истинно только при отсутствии действий; `AttackReevaluate()` может не завершаться, пока враг доступен. Поэтому выбранный ближайший охранник с активной атакой EPS способен оставаться неспособным выполнить запрос, хотя второй, более дальний, ничего не делает. Это вероятный механизм задержки, но не доказанная причина конкретного старого пользовательского наблюдения.

## Что меняет патч

**Только два участка точного действующего Lua 066S**, SHA256 оригинала `50640902ec4c25a2c85e5088d7231678b54445a847b41743c476974236d1d70f`:

1. Среди обычных существующих F-включённых и допустимых охранников читается `sprite.m_curAction.m_actionID` через `pcall`. Значение `0` используется **только как подсказка при сортировке** (возможный простой), не как доказательство отсутствия ручного приказа либо действий EPS. Ошибка чтения/отсутствие поля -> подсказка «неизвестно».
2. При двух и более кандидатах предпочитается возможный свободный охранник; среди одинаковых состояний остаётся прежний порядок «ближайший, потом слот портрета». Если нет подтверждённо свободного, поведение выбора не меняется.

**Важно:** никакого `ClearActions`, `Attack`, `Spell`, новых EEex hook, новых BCS, классов/китов/дуалов, снятия F-гейта. Lua продолжает писать только уже существующий запрос `BGX52_REQ_SLOT`. Отдать действие может только **ранее установленный BCS**, с `ActionListEmpty()`, `ModalState(NONE)`, F=ON, TTL, расстояниями и другими условиями. Защита ручных приказов остаётся консервативной, а при постоянно активной атаке ЕДИНСТВЕННОГО охранника эта правка не поможет.

**Ограничение:** `m_actionID==0` НЕ доказывает, что очередь EPS пуста, поэтому свободная подсказка сама по себе не даёт права на действие. Реальную готовность повторно проверяет прежний BCS. Никакой замены работающей логики EPS не допускается.

## Контроль и результаты

- Истинный live Lua 066S точный SHA256; BCS ожидаемый SHA256 `fb435d82e6c3e0ebea1d6a9532753921bd5411d70ac0677dc1fd8ec483380476`.
- 18/18 исходных реальных Lua 5.4 тестов; 17/17 прежних тестов нового Lua без единственного ожидаемого теста побайтного равенства исходнику.
- 15/15 новых сценариев выбора, F OFF, неверная область, модальные состояния, низкие HP, занятые заявки, отсутствие действия, отсутствие новых engine action.
- RED/GREEN на той же сцене: старый выбирает ближайшего занятого, кандидат — более дальнего свободного.
- `verify_release.py` сверяет каждый файл SHA256, точный diff ровно двух участков и совпадение hooks. Также поддерживает **исключительно read-only** `--game-root` для проверки точного живого baseline 066S. Ничего не устанавливает.
- В комплекте **нет** готового .tp2/EXE/автоинсталлятора: выпускать его до отдельного одобрения экспериментальной установки с полным WeiDU backup, SHA gate и откатом запрещено.
