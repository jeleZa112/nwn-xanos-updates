# BGXAI 066S: предотвращение двух одновременных запросов лекарю — исходник, не установка

**Состояние живой игры не изменено** (EET Foxx + SCS 35.21 + EEex 1.1.7 + EPS 18.4 + BGXAI 066S). Никаких `*.BCS`, установщиков, WeiDU, правок `override`, новых слушателей EEex или игровых действий. Работа продолжает уже подготовленный патч к существующему Lua 066S. Новый режим выбора по способностям по умолчанию ВЫКЛ.

## Что исправлено

После краткого Lua-резерва в BCS ещё мог оставаться запрос на заклинание (до 300 игровых тиков). Предыдущий кандидат исключал охрану/лечение одного актёра, но НЕ проверял противоположные **лечить ↔ наложить щит** заявки. При `BGX66Team.capabilitySourceVerified=true` добавлены ровно два условия в существующем выборе лекаря/защитного мага: наличие второго BCS-запроса должно быть `0`. При исключении EEex/неизвестном состоянии — отклонить новый запрос. При выключенном новом режиме обе проверки не вызываются и старая 066S ведёт себя прежним образом.

В файле `caster_pending_cross_request.diff` — только два изменения. `caster_pending_exact_diff.py` обращает оба изменения, восстанавливает побайтно предыдущий кандидат с контрольной суммой SHA256 `b339407826b9c0014a4ba8b4d63021aa48897e40af40f5a249bc78f69b407372`. Затем `arbiter_exact_diff.py` доказывает обратимость предыдущих пяти правок к предшествующему кандидату. `verify_release.py` проверяет также полный diff от реального исходного Lua установленной 066S.

## Проверки

Четыре новые модели сперва **все падали на исходнике предыдущего кандидата по целевой причине**, после двух условий прошли 4/4. Старый 066S 18/18; прежняя функциональность 17/17; предыдущая модель ролей, лекаря и конфликтов 32/32; новые 4/4. Проверяется настоящий Lua 5.4 через нативный запуск, а не парсинг Python строк. Проверка Lua синтаксиса через `texlua`.

Для повторной проверки в обычной папке (НЕ в папке Baldur): `py -3 verify_release.py`, `py -3 run_regression.py`, `texlua parse.lua M_BX43_066S_CAPABILITY_CANDIDATE.lua`.

## Что не доказано

По точному исходнику EEex 1.1.7 `EEex_Action.lua` blob `e7543274ed066b5abe3c58262105212f208d1595` и `EEex_Action_Patch.lua` blob `b9d4bf7ee97d1fffd1140f248b5244089a2b52f1` слушатель `EEex_Action_AddSpriteStartedActionListener` получает sprite/action, но НЕ происхождение manual/EPS и НЕ подтверждение пустой очереди. `EEex_Trigger_EvalConditionalStringAsAIBase` использует `m_pendingTriggers`; пока нет доказательства побочной безопасности для EPS, мы НЕ вызываем его. Никакое решение для включения нового режима в реальной игре не принято. Сохранять базовый EPS, не менять `ActionListEmpty()`, не предлагать автоматическую установку.
