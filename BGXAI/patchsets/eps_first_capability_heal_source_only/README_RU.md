# BGXAI: доработка действующего EPS/066S, без замены работающего ИИ

Дата: 14.11.2026. **SOURCE ONLY, К УСТАНОВКЕ НЕ ДОПУЩЕНО.**

## Зачем эта поправка

Установленная 066S использует `HEALER={3,8,11,14,15,16,17,18}` и `ARCANE={1,5,7,10,13,14,17,19}` при подготовке запросов лечения и Shield. Это неверная универсальная модель для всех китов, мультиклассов, дуалов, SCS respec, шамана и модовых способностей. При этом штатный BCS **уже проверяет** `HaveSpell(CLERIC_CURE_LIGHT_WOUNDS)` / `HaveSpell(WIZARD_SHIELD)` прямо перед применением.

В **существующем исходнике M_BX43.lua** сделан **один ограниченный diff**: вместо двух class-only предикатов вызывается `candidateCanUseSpell(actor, cls, spell)`. При наличии отдельного доверенного проверяющего функция допускает способность только при `true` (любое `nil`, `false`, число, ошибка — отказ). Если проверяющего **нет**, используется **точно прежняя** class-only модель 066S. Проверяющий по умолчанию `S.capabilityVerifier=nil`, т.е. новое поведение **выключено**.

**Ручные команды, EPS18.4, 061-guard, F, существующие классовые сценарии, BCS heal/shield, бафы, песни барда и предметы не переписаны.** Исходный Lua 066S и исходный BAF присутствуют в архиве отдельно, **не изменены**, для доказуемого diff/rollback. В архиве нет установщика, изменённого BCS или модификации игры.

## Что реально проверено

- SHA256 исходного Lua 066S: `50640902ec4c25a2c85e5088d7231678b54445a847b41743c476974236d1d70f` (совпадает с Windows read-only 081 пользователя).
- SHA256 исходного BAF 066S: `c678a70a08dbcff7584e0f2703aa8bed5ae5945856287666016ee47c9d6f69ae`.
- SHA256 кандидата: `c4e25bf6de7c3569b03657f3d48b5ddc9730c94ac6f63124bcc3f32cfb471e29`.
- Нативный Lua 5.4 mock-EEex: **18/18 базовых тестов 066S** и **30/30 проверок кандидата** (из них 17 прежних поведенческих регрессий, 4 статических/diff, 9 новых сценариев). `texlua` синтаксис PASS; статический контроль количества listener и отсутствия `ClearActions`/дополнительной Lua-отправки приказов PASS.
- Проверки на mock моделируют класс 21 Shaman, модовый класс, неизвестный kit, занятый или неготовый к лечению класс, ошибочный/ложный provider, защиту F OFF, сохранение Shield и запрет прямых действий Lua.

## Чего нет

**НЕТ доказанного источника истинного текущего `HaveSpell()` для каждого персонажа в работающей EEex 1.1.7 и EET**. Ни класс, ни имя кита, ни состояние предмета сами по себе не являются доказательством свободного спелла. Upstream `EEex_Trigger_EvalConditionalStringAsAIBase` существует в `EEex_Trigger.lua` v1.1.7 (blob `80da96ed5dc7cbcaa726631a3542ecafa533ec6f`), но его внутренняя работа использует `aiBase.m_pendingTriggers`; **отсутствие побочных эффектов на текущих игровых действиях пользователя не доказано**. Поэтому он намеренно НЕ вызывается из этого патча. Простой callback с `true` только в модельных тестах, а не в игровой установке.

**БОТОМ и улучшением живой игры это пока не является.** Если verifier отсутствует, поведение Lua обязано быть прежним. Текущая работающая 066S остаётся без изменений. Эта поправка не устраняет отдельное ограничение `FRONTLINE=2/6/12`; оно будет решаться по действительно доступным оружию/защитным способностям и ролям, не очередным списком классов.

## Продолжение по согласованному правилу №7

Сохранить единый исполнитель EPS как базу. Не писать с нуля, пока сравнительная проверка не докажет превосходство. Развивать **один ограниченный patchset**, не плодить диагностические версии. До любого доступа к игре — подтверждённый read-only контракт способности/свободной очереди, готовая точная проверка BCS и негативные проверки сценариев. Изменения EET/WeiDU/override только после отдельного разрешения с SHA-pinned backup/rollback. Не спрашивать повторно архивы EET или о повторном бое с Шанком.

Команда офлайн в распакованной папке: `python run_regression.py` (нужна библиотека liblua5.4 для Python ctypes, в Windows может потребоваться отдельная среда; без неё тесты не запускать).
