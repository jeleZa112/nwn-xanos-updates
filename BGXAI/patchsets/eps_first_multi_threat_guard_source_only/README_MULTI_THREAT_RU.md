## Что уже существовало (не переписано)

- EPS 18.4 выполняет штатные атаки, лечение, использование предметов, бафы, песни и поиск ловушек.
- BGXAI 062 содержит отдельную модель **одной угрозы** и один перехват. 072 проверяет доказанную личность атакующего и безопасность охраны. 078 отбирает лекаря на условиях EPS-first. 080 координирует **одну угрозу**, сохраняя существующее лечение. 082/083 запрещают приказы на основании одного только `m_actionID=0`.
- Действующая игра — BGXAI **066S + EPS 18.4**; файл `BGXAI080_EPS_FIRST_COORDINATOR.lua` в пакете **побайтно неизменён**, новый файл только добавляет к нему `reviewMultipleThreats()` и сохраняет старый `review()`.

## Единственная новая возможность в исходном коде

Когда **два разных врага** реально атакуют **разных союзников**, рассмотрение угроз производится совместно: не тратим сразу ближайшего свободного охранника на первую цель, если он единственный, кто способен помочь второй. Среди проверенно подходящих защитников распределяются **разные исполнители по разным подтверждённым противникам**, а приоритет у доказанного бойца тыла и затем более раненого союзника. При двух врагах, атакующих одного мага, допустимы два разных защитника на разных врагов. Защита тыла не запускается при HP ниже 25%, чтобы не конкурировать с приоритетным лечением EPS.

- Только F=ВКЛ, подтверждённо живой участник партии, способный действовать, подходящая роль, та же область, пригодная дистанция для конкретного пострадавшего.
- Реальный нападавший и пострадавший, время и актуальность угрозы должны быть независимо подтверждены; неизвестное/противоречивое = HOLD.
- Любой каст, баф, песня, воровской поиск, ручная команда, лечение или занятая EPS-очередь = HOLD. Отбор пользуется старым проверяющим `BGXAI072_EPS_FIRST_ARBITER.lua`.
- **Только advisory**: `orders_sent=0`, `locals_written=0`, `engine_dispatch=false`, не вызывает `Attack`, `Spell`, `ClearActions`, `UseItem`, не редактирует BCS/EPS/WeiDU. Нет второго лекаря, нет расходников и нового автообновлятора.
- Нельзя получить нужный `origin_verified=true` и `queue_empty=true` из одного `m_curAction.m_actionID=0` в установленной EEex 1.1.7. Данные 083 приводят к HOLD. Для реальной активной охраны нужен отдельный **доказанный** и проверенный мост, а не самовольное снятие проверки.

## Проверки

В настоящем интерпретаторе Lua 5.4: **143 адресных assertions** для multi-threat, **82** прежних assertions 080 на исходном модуле и **82** на новом коде с неизменённым `review()`; **15** старых Python тестов модели 062, **16** старых Python тестов 080 на сохранённом историческом BCS (не входит в публичный пакет), синтаксис Lua PASS. Новые сценарии: глобальное распределение, занятость EPS, защита ручных действий, критическое здоровье, двое врагов на одного мага, ошибка/подмена источника, разные области, нет доказательств очереди, попытка поддельного провайдера, неизменность переданных данных и OFF по умолчанию.

`python verify_multi_threat.py` проверяет неизменность оригинального 080, исходники по SHA и запускает 143+82+82 Lua assertions. Запускать в распакованной копии, где есть `texlua`; игра не нужна.

## Что не доказано

Нет реального EPS `manual vs automatic` происхождения и полного доказательства пустой очереди; разные участники могут быть заняты и F включён не у всех. Никакого игрового результата или обоснования установки на EET из этих тестов не следует. Новые функции не должны объявляться работающими, пока нет безопасного реального EEex/EPS контракта, отдельного согласия на установку, резервной копии и A/B проверки. Правило №7: продолжать доступную безопасную разработку в активном обращении.
