# BGXAI 066S → 080: мост подтверждённых попаданий, SOURCE ONLY

**Дата: 16.11.2026. Не устанавливать в игру.** Приоритет проекта — автономная командная охрана поверх действующей EPS 18.4. Это **не** новый модуль лечения, не ещё один установщик, не замена 066S и не команда атаки.

## Что было готово до этого

- В установленной 066S есть реальный `BGX43Probe.snapshot()`: два отдельных кольцевых журнала `events` и `guard_signals`. EEex регистрирует исходную пару attacker/target при `NONPARTY_WEAPON_HIT_ON_PARTY`; BGXAI создаёт `PASSIVE_GUARD_ADVISORY_ON_CONFIRMED_HIT` со ссылкой на `source_event_sequence`. У 066S `origin_verifiable=false` и `queue_verifiable=false`.
- BGXAI 072, 078, 080, 082–084 уже исследовали EPS/manual/idle и многократно подтвердили, что `m_actionID=0` не удостоверяет происхождение приказа; `ActionListEmpty()` лишь моментальный снимок. Мы не переписываем эти модули.
- В кандидате `BGXAI080_EPS_FIRST_COORDINATOR_MULTI_THREAT_SOURCE_ONLY.lua` было **нет источника реальных событий**: тесты подавали заранее придуманные `{verified=true,active_now=true}`. Такие флаги нельзя вычислить только из старых попаданий. Без этого новое распределение существовало исключительно на синтетических данных.

## Сделано

`BGXAI066S_080_CONFIRMED_HIT_BRIDGE_SOURCE_ONLY.lua` — **чистый read-only адаптер существующего снимка 066S**. Он сопоставляет оба журнала по номеру события, строго сверяет ID атакующего и пострадавшего, источник попадания, подтверждение и список членов партии. Разные размеры кольцевых журналов допускают пропуск осиротевшего сигнала, но не превращают его в доказательство. Повторы одного врага сводятся к его последнему подтверждённому попаданию; до шести записей. Нет обращений к EEex, регистрации хуков, записи `LOCALS`, отправки engine-действий, перехвата EPS или изменений файлов игры.

**Ограничения являются частью результата:** попадание подтверждает то, что *произошло*, но не доказывает, что атака продолжается сейчас; в 066S события не имеют игрового времени. Нельзя присвоить `freshness_verified=true`, `active_now=true`, `queue_empty_verified=true` или `origin_verified=true`. `M.readiness()` поэтому возвращает `HOLD_NO_ENGINE_DISPATCH`. `reviewMultipleThreats()` нельзя включить в активный режим только на основании этой истории. Результат нужен для безопасного приоритизирования фактических угроз при будущей интеграции, **не является готовым действующим ботом**.

## Воспроизводимые проверки

`texlua test_066s_snapshot_bridge.lua` — **261 локальное утверждение**, включая испорченные ID, ложные источники, повторные и устаревшие сигналы, связь с текущим многоцелевым координатором 080 и fail-closed шлюзом 082.

`texlua test_real_066s_snapshot.lua` — запуск **точного установленного исходника Lua 066S** (SHA256 `50640902…`) под существующей синтетической EEex-фикстурой; вызовы исходных `onWeaponHit`, `BGX43Probe.snapshot()` после событий от одного и двух противников; никаких дополнительных записей в игровые LOCALS.

`python run_bridge_tests.py` — полный повтор на чистой временной копии, проверяет **точные Git blob SHA** уже опубликованных исходников 066S, 080, 072 и 082; не скачивает файлы, не требует EET на компьютере. Для запуска в клоне ветки `bg-eet-ai` нужен `texlua`.

## Следующий настоящий рубеж

Дальнейшая *активная* командная охрана требует отдельно подтверждённой информации о **текущей атаке и безопасной EPS/manual-очереди** в запущенной EEex, а также согласованной установки и проверки в игре с сохранением рабочего 066S. До неё — без игры и без опасных `ActionListEmpty()` evaluators / `ClearActions()` в Lua. Старый однофайловый обновлятор и его pinned commit не менять ради очередного отчёта.
