# BGXAI 081 — проверка происхождения команд и очереди EPS (read-only)

**Дата:** 14.11.2026. **Игра:** последняя подтверждённая BGXAI 066S / EPS 18.4 / EEex 1.1.7 / EET SCS 35.21 Insane. **SOURCE ONLY.** Ничего не устанавливается в игру; не изменяются BCS, Lua, конфигурация EPS, WeiDU, F-охрана, резервные копии и обновлятор.

## Что установлено по исходным файлам

Законсервированный в библиотеке проекта настоящий кандидат активной 066S `M_BX43_066S_CASTER_CANDIDATE.lua` имеет SHA256 `50640902ec4c25a2c85e5088d7231678b54445a847b41743c476974236d1d70f`. Его точный исходник:

- регистрирует `EEex_Action_AddSpriteStartedActionListener(P.onStarted)` и `EEex_Sprite_AddBlockWeaponHitListener(P.onWeaponHit)`;
- читает `action.m_actionID` и `attacker.m_curAction.m_actionID`, но не доказывает, что очередь EPS пуста;
- устанавливает `P.manualOriginKnown = false`, а в отчёте `origin_verifiable = false`, `queue_verifiable = false`;
- **пишет** `BGX52_*` и `BGX66_S_*` LOCALS для BCS-запросов! Ошибочно говорить, что старая 066S целиком пассивная;
- не содержит доказанного классификатора пользовательской/скриптовой команды. ID действия или событие начала само по себе не определяет его происхождение.

**Внешняя документация:** EEex [Action](https://eeex-docs.readthedocs.io/en/latest/EEex%20Functions/Action/) отмечает слушатели `EEex_Action_AddSpriteStartedActionListener` как *undocumented*, а методы `EEex_Action_QueueResponseStringOnAIBase` — как способ **добавления** команд в очередь, не её чтения. Старый `EEex_GetActorCurrentAction()` описан в документации ранних x86-версий, НЕ доказано, что он применим к установленной 1.1.7. Чтение ID текущего действия также не равнозначно проверке полной очереди.

## Результат 081

`BGXAI081_ACTION_PROVENANCE_READONLY.lua`: чистая Lua-функция `observe(sprite)` читает только `sprite.m_curAction.m_actionID`, если он существует. Даже при ID 0 возвращает `action_origin='UNKNOWN'`, `queue_empty=nil`, `manual_command=nil`, `safe_to_dispatch=false`, ноль команд/записей/хук-регистраций. `arbitrate()` всегда `HOLD`, даже при подставленных благоприятных входных флагах. **Не подключена к игре.**

`audit_live_081.py`: SHA-locked CLI **ТОЛЬКО ЧИТАЕТ** два файла активной игры, сверяет SHA, проверяет наличие функций и известных `false`-флагов. **Не доказывает работу EEex во время игры**, только тождество файлов исходникам. При несовпадении выводит `BLOCKED_NO_GAME_CHANGE` и не делает никаких исправлений.

## Что необходимо доказать перед активным координатором

1. Поддерживаемый в **именно EEex 1.1.7** API возвращает состояние *очереди*, а не только ID текущего действия.
2. Из достоверного источника различаются **ручная команда игрока**, **EPS** и другая автоматика; неизвестный источник блокирует вмешательство.
3. Есть подтверждение, что не заняты баф, каст, лечение, песня, ловушки и критическое действие (отдельно от ID).
4. Точно известен атакующий, действие и область; EQ/проверка полиморфа/дуала не подменяются предположениями.
5. Только после отдельной проверки и согласованного установки обновления с SHA, WeiDU и внешним бэкапом можно менять 066S.
