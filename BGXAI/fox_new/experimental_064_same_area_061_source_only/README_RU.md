# BGXAI 064 — исправление выбора охранника из другой области (SOURCE ONLY)

**Дата:** 12.11.2026. **НЕ УСТАНОВЛЕНА. В реальной EET остаётся BGXAI 061.**

## Причина

Фактически установленная 061 подтверждена реальным игровым эпизодом «подошёл → бафнулся → убил». Но из исходного Lua обнаружен конкретный дефект: при получении подтверждённого попадания по союзнику `BGX52Bridge.prepare` сортирует охранников F=ON по координатам **без сравнения ARE**. Из-за этого охранник за дверью может быть выбран вместо доступного спутника в комнате. Сам BCS 061 применяет `InMyArea`, поэтому такой неверный запрос останется без движения. Дефект именно в Lua-выборе, не в EPS.

## Восстановление истинной 061 и контрольные SHA

- Зафиксированный GitHub исходник 056: SHA256 `35e450b6600f0fc65d47e535126a52e0303c360033307fa920776faec3f581ab`.
- Ровно две оригинальные замены 061 (TTL 90→300 и верхний предел игрового времени) дают SHA256 `fd39d23dc722b549c2af1eaf065541b2ed358a9714f2636b8cab4e45fe7dcec5` — **точное совпадение** с установленным Lua, ранее подтверждённым выводом WeiDU.
- Новый кандидат 064: SHA256 `bfee5278b5b69b1fb4a02e3fea321082b0238407789df83ec6bd2f78d7e19f4b`. Полный исходник кандидатной Lua в GitHub `BGXAI/fox_new/experimental_064_same_area_061_source_only/M_BX43_064_CANDIDATE.lua`.

## Ровно 4 изменения исходника

1. Строка версии в диагностике.
2. Если указатель области пострадавшего отсутствует либо функция `EEex_UDEqual` недоступна, вернуть диагностический отказ, не выдавать ложный запрос охраны.
3. В уже существующем цикле выбора добавить `EEex_UDEqual(obj.m_pArea, victim.m_pArea)==true` (под защитой `pcall`) как условие допуска охранника.
4. Уточнить текст отказа, если нет F=ON защитника в той же области.

**Не меняется:** единственный селектор, `BGX52_REQ_SLOT`/TTL/дедупликация, все BCS/EPS/WeiDU/другие моды, ручные команды, список API hooks, боевые приказы. Второй ИИ не создаётся. Если API сравнения области недоступен, кандидат откажет в защите — без runtime проверки **не устанавливать**.

## Исходники

- `BGXAI64_PATCH.py`: pure function, принимает только точный SHA установленной Lua 061, делает 4 уникальные текстовые замены, сравнивает итоговую SHA, восстанавливает исходник обратными заменами и доказывает, что другие байты не менялись.
- `BGXAI64_PREFLIGHT_READONLY.py`: проверка с интерфейсом для **одного существующего** `BGXAI_UPDATE.cmd` (ещё не привязана к его меню): последний WeiDU=061, установленный BCS/Lua и оба staged файла по SHA и побайтно, повторное чтение файлов, отчёт без записи. Сразу `authorized_to_install=false`, native EEex не считается проверенным.
- `BGX64_BRIDGE_PREPARE_NATIVE.lua`: буквальный `B.prepare` из кандидатной Lua с минимальной обвязкой для настоящего Lua 5.4. Длина и CRC32 фрагмента сверены с GitHub, совпадение подтверждено.
- `test_064_native.py`: 15 сценариев в реальном Lua 5.4, включая «ближайший за дверью», двух охранников, отсутствие API, исключения, таймеры и отсутствие боевых команд.
- `test_064_patch.py`: 11 тестов атомарной, обратимой текстовой замены и строгих SHA.
- `test_064_preflight.py`: 14 тестов read-only проверки, включая интерфейс для будущего единого автообновлятора, в фальшивом игровом каталоге.

Итог в одном запуске: **143/143 PASS** (103 предыдущих + 40 новых). Проверки выполнялись офлайн, не через пользовательскую EEex. Полный игровой рантайм 064 не проверен.

## Ограничения и следующий шаг

В прошлом игровом тесте пользователь уже получил `AREAAPI=function`, что доказывает *наличие* `EEex_UDEqual`, но не безопасность работы внутри on-hit callback. Не нужно заново присылать логи/архивы EET. Нужен безопасный read-only native preflight и только после него отдельная контролируемая установка в той же программе обновления и с резервной копией; согласие на установку не подразумевается. **Пока игра остаётся на рабочей 061.** Файл `manifest.json` совместим по схеме с существующим SHA-pinned источниковым загрузчиком, но активный `BGXAI_SYNC.ps1` и BOOTSTRAP_PIN не изменены; пункта 70 в меню пока нет. Не пытаться вручную запускать этот dev-комплект.
