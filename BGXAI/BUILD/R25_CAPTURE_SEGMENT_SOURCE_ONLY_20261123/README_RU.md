# BGXAI R25 — точное устранение зеркальных событий в офлайн журналах R2/R4

**SOURCE ONLY. NOT INSTALLED.** Код выполняет только функцию `inspect(data: bytes, source_type=...)`; не читает игру, не получает native handles, не меняет EPS, WeiDU, BGXAI_UPDATE.cmd, сохранения и runtime Lua.

## Доказанная проблема и решение

В реальном журнале `BGXAI_WEAPON_CONSOLE_20261122T131454167969Z.log` запись одного события R2 появляется дважды — как `INFO: LUA: [BGXW2] {...}` и сразу следом как **побайтно совпадающий** `INFO: LPRINT: [BGXW2] {...}`. Сырых `SLOTS` записей 32, **уникальных R2 последовательностей 16**. R4 даёт 16 самостоятельных `ACTIVE` событий. Дублирование в отчёте относится к каналам вывода, а не к дополнительным игровым атакам.

`BGXAI_R25_CAPTURE_SEGMENT_RO.py` удаляет **только** соседнюю пару `LUA→LPRINT` с одинаковым исходным JSON, отдельными метками источника и соседними номерами строк. Любая неожиданная непарная дубликация по `seq`, противоречие полей, второй READY, неверная схема или смешение персонажей приводит к `HOLD_UNTRUSTED_OR_AMBIGUOUS_CAPTURE`; ошибочные события не аггрегируются. Отдельно ограничены байты файла, строки и количество событий.

## Реальные результаты (только очищенная статистика)

| Источник | Состояние | События после устранения зеркал | Сегменты | Устранённые зеркала |
|---|---|---:|---:|---:|
| R2 `BGXAI_WEAPON_SLOTS_RAW_R2_LIVE_20261121.jsonl` | PASS OFFLINE | 10 `SLOTS` | 1 | 0 |
| R4 `BGXAI_WEAPON_ACTIVE_RAW_R4_LIVE_20261122.jsonl` | PASS OFFLINE | 4 `ACTIVE` | 1 | 0 |
| Консоль 22.11.2026 | PASS OFFLINE | 16 `SLOTS` + 16 `ACTIVE` | 2 по независимым источникам | 18 зеркальных пар, включая SESSION/READY |

Сырой журнал и Actor ID в публичный репозиторий **не включены**. Полный исходный отчёт остаётся в пользовательской библиотеке. Машинный очищенный итог — `R25_REAL_CAPTURE_SANITIZED_VERDICT.json`.

## Ограничения

* Поле `utc` в сохранённой R2 сессии содержит буквально `UNKNOWN`; R4 библиотечный файл при пересохранении не содержит UTC. Нельзя объявлять идентификатор игры доказанным.
* Создаётся *локальный для конкретного файла* токен из SHA256 байтов захвата, типа источника и позиции SESSION. Он разделяет офлайн сегменты **и не является реальным токеном сессии движка**.
* Консоль может содержать одновременно R2/R4 записи; совпадение актёра и номера `seq` не подтверждает нативную причинную пару или единое действие.
* `safeToDispatch=false`, `weaponSwitchAuthorized=false`, `sessionIdEngineAuthenticated=false`, `manualEpsQueueVerified=false` всегда.

## Проверки

`python -m unittest -v test_r25_capture_segment_ro.py` — 19 синтетических тестов, включая повреждённые и несовместимые зеркала; CI Windows+Linux, дополнительно SHA256 исходников и отсутствие игровых действий. Реальные файлы проверены локально, **их запрещено включать в публичный CI и каталог исходников**.

## Следующее

Использовать нормализованные R2/R4 сегменты как строгую offline историю `selected-only`, не пересчитывать альтернативный APR из R2/R4 и не считать `offlineCaptureToken` действительным runtime ID. Для живого переключения требуются доказанный источник session identity, боевые характеристики альтернативных слотов, effects и EPS/manual queue provenance, а для установки — отдельное typed согласие.
