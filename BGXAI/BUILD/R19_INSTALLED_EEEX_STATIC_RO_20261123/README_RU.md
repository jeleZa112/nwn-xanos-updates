# BGXAI R19 — аудит установленных EEex Lua-файлов без запуска игры

**SOURCE ONLY / READ ONLY / НЕ УСТАНОВЛЕН.** Никакого нового CMD, ZIP-запуска или изменения текущего `BGXAI_UPDATE.cmd`; TD15 и сохранения не затрагиваются.

## Почему R19 нужен

В R18 был найден официальный EEex **v1.1.7** контракт `CItem:getAbility()` и `CGameSprite:getLauncher()`; работа этих методов с игровыми CItem пока не проверена. Прямой `getAbility()` разыменовывает `item.pRes.pHeader`, а `getLauncher()` принимает нативный указатель на способность. Даже правильный Lua-текст не доказывает, что конкретный объект ресурса в момент вызова безопасен и жив.

**R19 строго отделяет** (1) точное совпадение установленного файла с официальным тегом по Git blob SHA, (2) эквивалентность после преобразования CRLF→LF/снятия BOM, (3) просто наличие необходимых определений в локальной модификации и (4) отсутствие/повреждение файла. Ничто из этого не даёт разрешения на нативный вызов или переключение оружия.

## Что делает `BGXAI_R19_INSTALLED_EEEX_AUDIT_RO.py`

- На Windows предназначен только для `C:\Games\BG_EET_FOXX_NEW`. **На компьютере пользователя ещё не запускался.** Функция `audit(..., fixture=True)` используется только для синтетических тестов.
- Читает `chitin.key`, `override/M___EEex.lua`, `EEex_scripts/EEex_Resource.lua`, `EEex_scripts/EEex_Sprite.lua`, `EEex_scripts/EEex_Action.lua`; не обращается к EXE, играм, BCS, журналу или `CItem`.
- Проверяет длины, доступность, отсутствие симлинков/junction/reparse, стабильность данных во время чтения, UTF-8 и отсутствие NUL. Источник размером более 2 МБ не принимается.
- Проверяет определения методов после исключения комментариев и строк Lua, чтобы записанные в комментарии названия функций не создавали ложный PASS.
- Фиксирует SHA256 установленного файла и его Git blob SHA1 как диагностические данные. Сверка upstream — с точными Git blob SHA тега v1.1.7, перечисленными в `UPSTREAM_EEEX_V117_CONTRACT.json`.
- Выводит JSON **только в stdout**; запись в игру и создание отчётов на диске отсутствуют. Нормальный результат при неизвестном модуле — `HOLD`, а не исправление файла.
- Не требует дополнительного `B3AttackInfo.lua`: этот модуль факультативный.

## Интерпретация результатов

| Статус | Что означает |
|---|---|
| `UPSTREAM_V117_EXACT_BYTES_STATIC_ONLY` | Все три Lua-модуля байт-в-байт равны upstream тегу, Lua API присутствуют статически |
| `UPSTREAM_V117_LF_EQUIVALENT_STATIC_ONLY` | Совпадают после преобразования окончаний строк (или BOM); байты установки отличаются |
| `LOCAL_EEEX_VARIANT_CALLSITES_PRESENT_STATIC_ONLY` | Ожидаемые методы есть, но установленный код отличается от официального |
| `HOLD_*` | Нет необходимых файлов/методов или источник недоступен/повреждён |

В **любом** случае флаги `safeToCallGetAbility`, `nativeResourceLifetimeVerified`, `safeToRegisterListener`, `dispatchAuthorized` и `weaponSwitchAuthorized` остаются `false`.

## Тесты

`python -m unittest -v test_r19_installed_eeex_audit_ro.py`

**36/36 локальных синтетических тестов PASS.** Здесь нет информации о текущем состоянии на пользовательском диске. Следом проводим CI на Windows/Linux. Больше старых игровых тестов не повторять.

## Дальнейший путь

После подтверждения статических файлов **через существующий единый обновлятор**, потребуется отдельный способ доказать безопасную готовность `CItem.pRes.pHeader` и локальную валидность `Item_ability_st`, не полагаясь только на `pcall` (ошибочный нативный указатель способен обрушить процесс ещё до Lua-обработчика). Пока такой способ не найден, R18 не устанавливать; допустима только дальнейшая исходная офлайн-разработка и безопасные альтернативы на основе уже имеющегося R3 ITM-скана. Ни установку, ни бой на этом этапе не запрашиваем.
