# BG_EET_RU — V114: реальная x64-точка броска атаки, SOURCE ONLY

**Дата:** 23.11.2026. **Статус:** SOURCE RESEARCH + OFFLINE SELFTEST PASS; **никакой установки**, Windows LIVE V114 нет. Действующий Windows-обновлятор остаётся **V112**, игровые файлы не менялись.

## Что стало известно после V113

Найден современный, **невлитый** PR [Bubb13/EEex #136 «EEex_AttackOnce»](https://github.com/Bubb13/EEex/pull/136) (открыт с 04.07.2026, по проверке 23.11.2026 статус `open`, `merged=false`, PR head `67766626c50abcac302f98a777bff5d9587cb765`). Он намерен *изменять* действие `Attack()` — завершать его после первого реального броска, править d20, урон и расход стрел при включении специального действия. **Это не пассивный наблюдатель; устанавливать/заимствовать реализацию нельзя.**

Из его диффа `EEex_Sprite_Patch.lua` и `InfinityLoader.db` получили конкретные источники сведений:

| Точка | Что доказывает исходник PR | Чего ещё не доказывает |
|---|---|---|
| `Hook-CGameSprite::Hit()-AttackOnceBaseAttackRoll` | В `CGameSprite::Hit()` есть участок, где исходный d20 находится в `di`; PR передаёт кандидаты на атакующего (`rbx`) и цель (`r14`). | Что установленный EEex имеет эту точку; связь с CItem и строкой журнала; пассивная безопасность нового хука. |
| `Hook-CGameSprite::Swing()-AttackOnceHitCall-1/2` | Два пути перед вызовом Hit, на которых PR комментирует `r8/r9` как выбранное оружие/способность и отдельно управляет расходом боеприпасов, в том числе при промахах. | Что этот снимок можно надёжно и без изменений перенести до d20; отдельный вызов для каждого исхода во всех модифицированных боях. |
| `Hook-CGameSprite::Hit()-FormatRollCall` | Уже существующая метка, связанная с формированием текста результата броска (в pinned EEex). | Что этот вызов создаёт запись в `combatLog` с неизменным row ID. |

**Важная коллизия адресации:** `AttackOnceBaseAttackRoll` и `FormatRollCall` в `InfinityLoader.db` используют одинаковый шаблон байтов `488D4DD08D7801`, но `Operations=ADD 7` и `ADD 18` соответственно. Это близкие позиции **одного поиска**, а **не** общий идентификатор броска и не разрешение безопасно совмещать нативные хуки. Не копировать байты, регистры и смещения в установленный EEex.

Для самой строки журнала найден только косвенный исторический след: в документации EEex классов **x86** упоминается `CScreenWorld::DisplayText`; подтверждения пригодного callback именно на **x64 append**, с неизменным ID сообщения и одинаковым токеном атаки, нет. UI-поле `combatLog[rowNumber]` — индекс отображения, **не ID движка**. Нельзя использовать отрисовочный hook как производитель событий: частота вызовов зависит от UI, а в старых версиях отмечались задержки FPS.

## Конкретный контракт будущего пассивного механизма

Безопасный обработчик должен срабатывать **раз на каждый реально совершённый бросок**, включая промах; передавать `attack_id`, ID атакующего и цели, исход броска, руки/способность, точный `CItem` оружия и пускового оружия **до переключения предметов**; а на этапе **создания** сообщения журнал должен получать тот же `attack_id` и новый неизменный `journal_row_id`. Слово «ПРОМАХ» уже понимает установленный V101 FULL/BRIEF; проблема только в надёжной подписи оружия, не в переводе результата.

Если ID отсутствует, неоднозначен, изменён по дороге или событие относится лишь к урону, то **не подставлять оружие**. Не менять d20/урон/боеприпасы, не писать в `combatLog`, не вмешиваться в FPS и не включать агрессию. Для будущего опыта понадобятся точные SHA игрового x64 EEex, проверяемый rollback и отдельное введённое пользователем согласие.

**Сценарии приёмки:** промах из лука; попадание обычным мечом; 2–10 APR; две руки; несколько бойцов атакуют одну цель; переключение лук↔меч между выпуском и прилётом стрелы; два снаряда в полёте; натуральные 1/20; задержка текста; единичный бросок без строки; повторяющиеся строки текста. Изменения в UI и BCS при этом равны нулю.
