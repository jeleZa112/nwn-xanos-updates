# BG_EET_RU — V129: исправление архитектуры перехвата атак (24.11.2026)

**Статус:** реальный UI-захват V126 — 72 строки, PASS; точное определение оружия каждого попадания/промаха — ещё HOLD. V129 — разработка исходников и тестов, **не** установка нового хука.

## Новое существенное открытие из реальной игровой сборки

Исходный файл: пользовательский `SEND_TO_CHATGPT_BG_EET_RU(20261124-164826).zip`, ресурс `19_V68_COMBAT_CODE/functions/0039DA50_0039E9DC.bin`, SHA256 `19c1d11b7ac41d261d22b19506b3570427e356544e48f2e2c622c1efdb74cc79`.

Оригинальный `CGameSprite::Hit()` содержит ветвления:

| Адрес | Машинное действие | Смысл |
|---|---|---|
| `0x39E694` / `0x39E699` | `cmp eax,0x182` → `je 0x39E7A0` | Ветвь к принудительному значению |
| `0x39E69F` / `0x39E6A4` | `cmp eax,0x502` → `je 0x39E7A0` | Вторая ветвь к тому же блоку |
| `0x39E7A0` / `0x39E7A5` | `mov esi,1` → `mov eax,esi` | `eax=1` |
| `0x39E7AE` / `0x39E7B1` | `cmove eax,esi` → `test eax,eax` | Значение остаётся 1 |
| `0x39E7B3` | `jne 0x39E855` | **Перепрыгивает** `0x39E84B` |
| `0x39E84B` | `call 0x204C60` | Условная передача `CMessageHandler::AddMessage()` |

Эти переходы сверены непосредственно с байтами пользовательского бинарного ресурса. **Установлено:** существование ветвей, обходящих указанный `AddMessage` внутри `Hit()`. **Не установлено:** что именно означают константы `0x182/0x502` для игры и как часто эти ветви используются при попаданиях или промахах. Поэтому прежнее предположение, что этот callsite всегда представляет *каждую* атаку, снято.

## Что разработано
- `conditional_hit_message_v129.py`: проверка исходной функции по SHA/CRC, уникальности ZIP, точным байтам 16 инструкций и вычисленным адресам пяти относительных переходов. Отдаёт `message_callsite_is_universal_event_source=false`. Только чтение.
- `test_conditional_hit_message_v129.py`: негативные тесты на каждое намеренно изменённое место и контроль отсутствия игрового подтверждения.
- `BG_EET_RU_V129_ATTEMPT_LEDGER.lua`: новая чистая Lua-модель, фиксирующая вход в попытку атаки, **необязательное** сообщение и выход. Если `AddMessage` отсутствовал, это не равно MISS; исход остаётся `UNVERIFIED`. Содержит ограничители буферов и `SESSION_HOLD` при неоднозначном кадре. Не загружается игрой.
- `test_v129_attempt_ledger.lua`: реальные Lua 5.4 тесты отсутствующего сообщения, сообщения с проверенным callsite, двух потоков/кадров, несоответствующей последовательности, выхода, переполнения.

## Правильный дальнейший алгоритм
1. Будущий источник **каждой попытки атаки** должен быть независим от `CMessageHandler::AddMessage`. Кандидат: вход `CGameSprite::Hit()` `0x39DA68` с точным item/attacker/target и парным выходом, но для него ещё необходимо доказать Win64 ABI и состояние настоящего `CItem` в момент вызова.
2. Тот же поток/кадр должен сопоставлять необязательный `CMessage` только при наличии точного соответствия. Событие без сообщения всё равно является зарегистрированной попыткой, но исход атаки без отдельного доказательства **НЕ определён**.
3. Для отображаемой строки UI требуется дополнительный проверяемый ключ через обработчик/очередь сообщений. Текущие 72 строки с номерами сохранены в `bg-eet-ru/CURRENT/BG_EET_RU_CURRENT_V126_LIVE_72_ROWS_20261124_RU.md`. Нельзя делать соединение по соседству, имени актёра или разнице во времени.
4. Не переустанавливать V126, не просить пользователя повторять бой. `BG_EET_RU_UPDATE.cmd` остаётся V128. Никаких новых изменений игры без отдельного точного разрешения, резервных копий, проверки владельца EEex JIT-патча и безопасного отката.

**Критерий успеха:** в реальной игре появляется надёжная связь `Hit attempt ↔ [optional CMessage] ↔ visible combatLog row` для попаданий и промахов, а не только рост числа проверок.
