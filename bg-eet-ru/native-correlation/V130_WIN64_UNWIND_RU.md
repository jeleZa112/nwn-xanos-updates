# BG_EET_RU — V130: безопасное место входа Hit() и Windows unwind (SOURCE ONLY)

## На чём основано

Реальная пользовательская сборка Baldur.exe: SHA256 `fc821a4806a0305b84fd85f1aad2bd472c8db642ed34b4494ae62351cae1c580`. Точный образ функции `CGameSprite::Hit()` в ZIP: SHA256 `19c1d11b7ac41d261d22b19506b3570427e356544e48f2e2c622c1efdb74cc79`. После V129 известно, что `AddMessage` в `0x39E84B` условен — не источник каждой попытки атаки.

### Новый анализ настоящих байтов

| Адрес | Инструкция (реальные байты) | Значение |
|---|---|---|
| `0x39DA50` | `48 89 5C 24 20` | первоначальное сохранение RBX |
| `0x39DA5A ... 0x39DA65` | `push rbp/rsi/rdi/r12-r15; mov rbp,rsp` | формирование кадра функции |
| `0x39DA68` | `48 81 EC 80 00 00 00` | `sub rsp,0x80`; прежняя точка наблюдения **может находиться внутри Windows unwind prologue** |
| `0x39DA6F` | `4C 8B F2 48 8B D9` | две простые MOV, 6 байт: `r14←rdx`, `rbx←rcx`; **новый потенциальный участок** |
| `0x39DA75` | `48 8D 15 A1 C9 24 00` | RIP-relative LEA, **запрещено сырое копирование в trampoline** |
| `0x39DA7C` и `0x39DA83` | `esi←r9d`, `r15←r8` | аргументы ещё нужны до внутреннего вызова |
| `0x39DA86` | исходный `call 0x3FCD70`, в текущей игре уже заменён EEex на JMP | **нельзя перезаписывать или заявлять ownership** |
| `0x39E9A7 … 0x39E9B9` | восстановление `rsp`, `r15-r12`, `rdi/rsi/rbp`, `ret` | normal return, исключения / другие ветви ещё требуют проверки |

По Win64 ABI до исходных MOV регистры `RCX/RDX/R8/R9` потенциально несут аргументы функции, но **реальная семантика CItem, качество указателей, XMM, unwind и целостность кадров всё ещё HOLD**. Самого факта 6 безопасно переносимых байт недостаточно для игрового native-хука.

## Что реализовано

`bg-eet-ru/native-correlation/pe_unwind_entry_gate_v130.py`:
- Загружает только read-only локальный **Baldur.exe**, проверяет полный SHA256 точной сборки.
- Самостоятельно разбирает PE32+ AMD64, таблицу секций, exception directory `.pdata`, unwind info `.xdata`, границы именно `CGameSprite::Hit()`.
- Сверяет настоящий машинный пролог, кандидата длиной 6 байт, опасную RIP LEA и обычный эпилог.
- Проверяет `SizeOfProlog`, Win64 `UNWIND_CODE`, frame register / offset и наличие EH/UH/CHAININFO.
- Исходное `0x39DA68` допускается только как известное место инструкции выделения стека, **не предлагается для установки**. Точка `0x39DA6F` получает `POST_PROLOGUE_CANDIDATE_STATIC_PASS_RUNTIME_HOLD` только если `.xdata` подтверждает нахождение за прологом и не обнаружены признаки сложного unwind.
- Повреждённые секции, лишняя или отсутствующая `RUNTIME_FUNCTION`, несовпадение SHA/байт, другая архитектура — немедленный отказ. По умолчанию полный SHA Baldur.exe обязателен.
- **Никогда** не заявляет `native_hook_install_allowed=true`, даже при всех PASS. Нет обращения к процессу или установки хуков.

`test_pe_unwind_entry_gate_v130.py`: изолированные синтетические PE64-файлы со специальной `.pdata/.xdata`, позитивный и негативные контрольные случаи (повреждение оригинальных байтов, другое число секций/архитектура, слишком длинный пролог, обработчики, неверная таблица исключений, неверный исходный SHA). В GitHub CI пользовательский EXE не публикуется.

## Ограничения и следующий этап
В пользовательских ZIP доступны настоящие **байты функции**, но **не полный EXE с `.pdata/.xdata`**. Поэтому на данный момент можно проверить точные инструкции, но **нельзя утверждать реальную длину пролога или соответствие Windows unwind информации**. Нельзя переносить положительный результат синтетического PE на игру.

Следующий шаг после CI — включить *этот* read-only PE gate в **существующий один обновлятор** или другой уже доказанный безопасный путь получения результата без повторного 14-этапного аудита; пользовательский запуск только когда это реально открывает установку native-пилота. Затем доказать Win64 ABI, EEex owner, сохранение XMM и unwind, atomic rollback, точный CItem и соответствие реальной строке `combatLog`. Новое явное разрешение обязательно.
