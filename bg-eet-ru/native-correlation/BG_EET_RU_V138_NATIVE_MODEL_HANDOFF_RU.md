# BG_EET_RU — V138: работающий нативный учёт отдельных попыток, SOURCE ONLY

## Что именно создано

V138 **не ставит хук** в Baldur's Gate и не меняет боевой журнал. В отличие от предыдущего контракта V137, здесь появился **реально исполняемый код на C** для учёта попыток атаки, отдельно компилируемый для Win64. Он является нижним уровнем будущего моста, но **не подключён к EEex**.

Файлы в `bg-eet-ru/native-correlation/`:

- `v138_native_attempt_ledger.c`: компактный накопитель, отдельный идентификатор `session/thread/frame/seq`, строгий LIFO для вложенных атак одного потока, одновременные кадры разных потоков, мгновенное копирование восьмибайтных RESREF, раздельные `weapon/launcher/ammo`, `ability`, необработанный байт выхода и API для **явно переданного** токена рендеринга. Никаких автоматических выводов о HIT/MISS, CMessage или UI.
- `v138_test_support.py`, `test_v138_native_ledger_core.py`, `test_v138_native_ledger_adversarial.py`: **22 испытания реального скомпилированного C**, включая 500 перемешанных входов/выходов, 512 записей, переполнение, неверные frame/seq, межпоточные коллизии, порчу RESREF, повторные токены и неизменность скопированного оружия. На Linux грузит изолированную ELF `.so`; на Windows собирает отдельную Win64 DLL через clang+lld-link **только для тестирования**. Никогда не грузит DLL в игру.
- `v138_native_abi_preflight_ro.py`: отдельная проверка реального архива V136 и Win64 COFF. Проверяет восемь машинных точек исходного `Hit()`, обход условного `AddMessage`, старую .xdata, точную исходную строку UI `clean(combatLog[rowNumber])`, наличие и корректность `IMAGE_RUNTIME_FUNCTION_ENTRY` в `.pdata` и компиляторной `.xdata`.
- `test_v138_native_abi_preflight_ro.py`: **18 проверок** целостности COFF с негативными изменениями архитектуры, unwind-разделов, записей, relocation, версий и исходных данных. Тест реального пользовательского ZIP запускается локально, но **ZIP в GitHub не передаётся**.
- `.github/workflows/bg-eet-ru-v138-native-ledger.yml`: сборка Win64 COFF и тесты для Linux и Windows; никаких игровых файлов.

## Фактические исходные доказательства

Пинованный ZIP пользователя `SEND_TO_CHATGPT_BG_EET_RU(20261125-162331).zip` проверен повторно без новых запусков игры. Реальные исходные байты `Hit()` SHA256 `19c1d11b...`, подтверждены переходы: `r9d → esi` для ability в `0x39DA7C`, `r8 → r15` для item в `0x39DA83`; наблюдатель V136 подтверждает `FirstCall` E9 и отдельные вход/выход. Точки 0x39DA6F и 0x39E99B остаются **гипотезами** точек будущего callback: безопасное внедрение не доказано. `0x39E7B3` пропускает условный вызов `0x39E84B`; его нельзя использовать как общий идентификатор промаха. UI показывает `clean(combatLog[rowNumber])`, без реального per-attempt token.

Из исходника EEex `EEex_Sprite_Patch.lua` следует, что `Hit()-FirstCall` уже занят: он записывает `r15` и `rsi` в глобальные SavedItem-поля. Это **не** потокобезопасный идентификатор конкретного попадания. Указатель CItem нельзя хранить или передавать в асинхронный рендер. Новый C-модуль поэтому принимает **собственную** структуру `BG_Resref { bytes[8], length }` с явной длиной, сразу копирует данные и не читает девятый байт. **Эта модельная структура не является доказанным форматом игрового CResRef**; запрещено приводить к ней реальный `CItem` без отдельной проверки layout.

## Почему Win64-компиляция ещё не равно работающему хуку

Первый эксперимент компиляции с `-ffreestanding` создавал COFF без `.pdata/.xdata`; такой объект отвергается. С дополнительным `-funwind-tables` компилятор создаёт нужные разделы (локально: две unwind-записи). Однако присутствие .pdata/.xdata в отдельном объекте **не доказывает**, что JIT/EEex регистрирует эти таблицы в *процессе игры* с `RtlAddFunctionTable`, что работает SEH и что сохраняются GPR/XMM/RFLAGS/stack alignment именно в игровом trampoline. V138 не выполняет `RtlLookupFunctionEntry` в другом процессе и не утверждает, что способен это сделать извне без внедрения.

## Предохранители и реальные ограничения

- `BG_THREADS=24`, `BG_DEPTH=16`, `BG_RECORDS=512`; превышение лимита, неверный порядок кадров, повторный токен или конфликт возвращают ошибку, а не связывают случайную атаку. Одновременный доступ защищён **неблокирующей** атомарной блокировкой: при конкуренции возвращается `BUSY`, никакого ожидания игрового потока.
- В API нет получения `HIT/MISS` из raw_return `0/1`: байт сохраняется только как сырой. Реальный смысл должен быть калиброван на отдельных подтверждённых результатах.
- `bgv138_direct_render(session,seq,token)` принимает токен *от будущего доказанного* источника UI; сейчас эта функция тестируется **синтетически**. Она **не** извлекает токен из строки, имени, времени, соседнего события или условного AddMessage.
- Глобальная таблица хранит только локальные копии данных, не CItem-указатели. Нет кода `WriteProcessMemory`, EEex JIT, загрузки в игру, изменения TLK/UI/EXE или пользовательских сохранений.
- Ни один тест V138 не подтверждает регистрацию runtime unwind для живого JIT или доставку реального прямого токена в `combatLog`. Эти пункты остаются **HOLD**. `safe_to_install=false`, `gameplay_verified=false`.
