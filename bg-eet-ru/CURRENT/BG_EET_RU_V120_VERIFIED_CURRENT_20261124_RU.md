# BG_EET_RU — единое состояние после V120 и независимого анализа

**Дата:** 24 ноября 2026. **Задача:** точные русские сообщения боевого журнала EET, включая название оружия/боеприпаса, без ложной привязки чужого броска. **Правило:** один обновлятор `BG_EET_RU_UPDATE.cmd`, один отчёт `SEND_TO_CHATGPT_BG_EET_RU.zip`, максимально возможная диагностика за один проход; не спрашивать подтверждения для безопасных READ ONLY этапов. Никаких отдельных Windows-скриптов и множества повторных запусков. Эта контрольная точка — **анализ**, не игровой патч.

## Реальное состояние

- В присланном архиве `SEND_TO_CHATGPT_BG_EET_RU(20261124-031007).zip`: **129 записей, CRC PASS**. Основной отчёт: `58_FULL_SPECTRUM_STATIC_AUDIT.json`.
- Итог V120: `STATIC_EVIDENCE_COLLECTED_RUNTIME_JOIN_HOLD`, ошибок коллектора **0**, записей в игру **0**, новых хуков **0**, `gameplay_result=NOT_TESTED`.
- Независимый офлайн-аудит: **99/99 проверок PASS**. Проверены 30 индивидуальных SHA256 и длины сохранённых фрагментов, пять прямых `CALL`, два `LEA` на одну виртуальную таблицу, семантика ряда методов, целостность ZIP и безопасные ограничения. Эти 99 проверок — проверки **доказательств и статического кода**, не 99 игровых сценариев.
- Действующий EXE: SHA256 `fc821a4806a0305b84fd85f1aad2bd472c8db642ed34b4494ae62351cae1c580`; активная `InfinityLoader.db`: `5e4fb47ed1575255f79a03e7b4edfcc3bd9ee5dcb700059e0833aa8d4fae3ca0`.
- V116 подтвердила, что RVA `0x204C60` совпадает с сигнатурой `CMessageHandler::AddMessage` в установленном EEex Loader DB.

## Новые выводы из архивных байтов (не гипотезы о runtime)

1. В обработке броска `0x39DA50` создаётся 48-байтный объект: `0x39E7D9` → виртуальная таблица `0x597CD0`, ID атакующего копируется в поля `+0x08/+0x0C`, строки — в `+0x10/+0x18`, дополнительные значения — `+0x20..+0x2E`; затем `0x39E84B` вызывает `0x204C60`.
2. В обработке урона `0x38FBF0` точка `0x390DF9` использует **ту же виртуальную таблицу**. Ещё четыре прямых вызова `0x204C60` в этой функции подтверждены относительными смещениями из реального кода.
3. В `0x204C60` инструкция `call [rax+0x08]` получает категорию сообщения через виртуальный метод и затем выполняется ветвление. Это доказывает маршрут класса сообщений, а не ID конкретной записи боевого журнала.
4. Для таблицы `0x597CD0` первая семёрка: слот 0 `0x1A4460` (деструктороподобный метод; освобождение 0x30 байт), слот 1 `0x14DD50` (возвращает слово из **глобальных данных** RVA `0x58D970`, само значение в ZIP неизвестно), слот 2 `0x117B80`, слот 3 `0x1E4C50` (возвращает байт из глобальных данных `0x5992A3`), слот 4 `0x20AEA0`, слот 5 `0x21AA80`, слот 6 `0x2110B0`.
5. Метод `0x2110B0` читает текстовые поля `+0x10/+0x18`, флаги `+0x20..+0x2E` и вызывает RVA `0x2EEFE0`. **Имя и роль функции `0x2EEFE0` не подтверждены**: называть её добавлением строки в `combatLog` нельзя.
6. **Исправление интерпретации V120:** 48 соседних указателей не следует считать 48 методами одной таблицы. На слотах 7, 14, 21, 28, 35, 42 повторяется адрес деструктороподобного метода `0x155000`, а на смещении +2 в каждой семёрке повторяется `0x117B80`. Это сильно указывает на **семь соседних таблиц примерно по семь слотов**, из которых последняя захвачена не полностью. Первая таблица уверенно идентифицирована по точным `LEA` в функциях броска и урона. Конкретные C++-имена классов не доказаны.
7. Показатель `all_byte_candidates=977` — **сырые совпадения байтов**, они не являются 977 подтверждёнными вызовами или событиями. Независимо доказаны **пять** известных вызовов из архивных функций.
8. В `UI.MENU` обнаружена привязка `combatLog[rowNumber]` и функция `BG_EET_RU_LogView`. Сквозного ID «отдельный бросок → отдельный ряд» в собранных данных не доказано.

## Нельзя утверждать на основании V120

- Что `0x2EEFE0` обязательно добавляет запись именно в `combatLog`.
- Что глобальное WORD по `0x58D970` имеет определённое значение (например, канал 1 или 2): из данного ZIP это **не следует**.
- Что в объекте 48 байт присутствует уникальный ID атаки или точные RESREF оружия/боеприпаса: в обнаруженной структуре таких полей **не показано**.
- Что обработчик `EEex_Sprite_AddAlterBaseWeaponDamageListener` вызывается при промахе: имеющиеся свидетельства поддерживают только событие попадания/урона.
- Что решение для всех попаданий, промахов, стрел, двуручного/парного оружия и нескольких атак одновременно готово: **нет игрового PASS**.

## Правильное направление реализации без очередных 20 запусков

**Ключевое архитектурное ограничение:** не сопоставлять независимые события по имени атакующего, таймеру, последней записи, видимому тексту или предполагаемому порядку. Самый перспективный кандидат — обогащать исходный текст сообщения **на этапе создания того же сообщения**, только если двигатель в этом же событии предоставляет достоверный конкретный `CItem`/RESREF оружия и боеприпаса. Если его там нет, сохранять оригинальное сообщение. Это **проектное предложение**, не подтверждённый хук/патч.

Остаются только два независимых доказательных барьера:

1. Проследить, что выполняет `0x2EEFE0` и когда текст сообщения действительно достигает конкретной строки журнала. Пока доступный срез заканчивается вызовом `0x2EEFE0`. Не требовать нового Windows-сбора только ради этого, если нет одновременно спланированного полного пилота.
2. Получить exact weapon+launcher на **каждом броске включая промах**, в момент конструирования того же сообщения. Не использовать текущий hit-only источник как универсальный.

Прежде чем запрашивать участие пользователя: отдельно провести максимально полный анализ архивных данных, исследовать доступные API EEex/исходники, построить готовый guarded-пилот с обратимостью, точными SHA и проверками на синтетических случаях. **Одна просьба об одном комплексном игровом тесте** допустима только после готовности безопасного, явно одобряемого пилота. Тестовый набор должен покрывать попадание, промах, стрелу/лук, ближнее оружие, парное оружие и несколько атакующих без подмены результатов. Без разрешения — никаких игровых изменений.

В проекте BG Voice RU продолжается независимая озвучка; её файлы, голоса и инструменты не затрагивались. BGXAI и сохранения также нетронуты. Двоичные игровые фрагменты остаются только в приватном ZIP пользователя и не размещаются в публичном GitHub. Этот документ содержит только производные выводы и адреса.
