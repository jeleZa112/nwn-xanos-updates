# BG_EET_RU — единый большой пакет V4 (24.11.2026)

**Статус: SOURCE/MODEL PASS, runtime Windows ещё не подтверждён, игровой перехват НЕ установлен.**

## Цель
Получать точное оружие конкретной попытки атаки в EET, в том числе промаха, и затем сопоставлять событие с правильной видимой строкой русского боевого журнала. Изменения BG Voice RU, BGXAI, сохранений, EXE, TLK, UI и игровых скриптов запрещены без отдельного разрешения.

## Что впервые сделано в этом пакете

1. По точному ранее присланному V120 ZIP проверена цепочка внутри `CGameSprite::Hit()`:
   - `0x39DA68` — безопасная с точки зрения переноса инструкция после установки `RBP`, при исходных `RCX/RDX/R8/R9`;
   - `0x39E7D9` — формирование vtable для сообщения `0x597CD0`, `0x39E7E0` — запись vtable в объект;
   - `0x39E848` — передача объекта сообщения через `RDX`, `0x39E84B` — реальный вызов `CMessageHandler::AddMessage()`;
   - `0x39E996` — кандидат очистки контекста на обычном выходе.
   - **Важно:** та же vtable используется и функцией расчёта урона (`0x390DF9`). Поэтому vtable сама по себе НЕ идентифицирует бросок: нужен точный исходный callsite внутри `Hit()` плюс поток и кадр.
2. Реальная Lua 5.4 модель `BG_EET_RU_THREAD_FRAME_BRIDGE_V4.lua` проверяет `(thread,frame)`, а не только адрес стека. Она хранит копию RESREF, номер способности, идентификаторы атакующего и цели. Защита от дублирования и неоднозначности, ограничение 24 потоков, 128 кадров, 8 сообщений на кадр. Ошибки → `HOLD`, строка журнала никогда не модифицируется. 6410 assertions плюс тесты граничных бюджетов.
3. `windows_live_hit_inventory_ro.py`: готовый исходник **внешнего read-only Windows-сканера**. Через стандартные Win32 Tool Help API и `ReadProcessMemory` без внедрения кода получает ограниченные участки памяти, сверяет SHA256 on-disk EXE, точный путь, оба native CALL, существующий EEex JMP, семь адресов vtable, повторяет чтение. Только права `PROCESS_VM_READ` и `PROCESS_QUERY_LIMITED_INFORMATION`; API записи, изменения защиты памяти, инжекции и приостановки потоков не используется. Никакого игрового контента в отчёт не выгружается, только статусы, контрольные суммы и наличие хуков. Windows CI может испытать **настоящий** `ReadProcessMemory` на своём безопасном процессе.
4. Один `one_big_batch_v4.py` автоматически выполняет предыдущие 9 этапов и 7 новых, включая 25 pinned native-кодов, Lua-модель, 15 групп adversarial Windows-reader тестов/500 намеренных повреждений, запрет записи и повторную проверку контрольных сумм. Отдельный сбой не маскирует результат других этапов.
