# BG_EET_RU — исправленный same-Hit native пилот, источник V1

**Статус: SOURCE READY / RUNTIME HOLD / GAMEPLAY NOT TESTED.**

Это исследовательский код (Python + Lua, два файла и тесты), **не установщик**. Он не изменяет ни `Baldur.exe`, ни EEex, ни сохранения, ни перевод. Для одного Windows-запуска пользователь по-прежнему использует только `BG_EET_RU_UPDATE.cmd`; этот пакет запускать на ПК пользователя не требуется.

## Критически важное исправление

Старая предложенная точка `0x39DA75` содержит 7-байтовый `lea rdx, [rip+disp32]`. В исходниках EEex `EEex_HookBeforeRestoreInternal()` переносит байты через `EEex_StoreBytesAssembly()` без адаптации RIP-relative displacement. Перенос такой LEA в JIT-трамплин вычислил бы **не тот адрес**. Использовать эту точку **запрещено**.

Вместо неё выбран RVA **`0x39DA68`**, исходные байты `48 81 EC 80 00 00 00` (`sub rsp,0x80`). Эта инструкция не зависит от RIP. У функции уже установлен RBP; в этот момент исходные Windows x64 параметры: `RCX` атакующий, `RDX` цель, `R8` CItem*, `R9` индекс способности. Важно: `RBX` и `R14` будут заполнены **после** новой точки — читать их здесь нельзя.

Выбранная цепочка:

| Назначение | RVA | Ожидаемые исходные байты | Проверка |
|--|--|--|--|
| Захват CItem + ability | `0x39DA68` | `4881ec80000000` | Без RIP-relative; кадр RBP уже создан |
| Существующий EEex FirstCall | `0x39DA86` | `e8e5f20500` на диске | Уже перехвачен EEex; **не трогать** |
| Сообщение → AddMessage | `0x39E84B` | `e81064e6ff` | В том же `Hit()`; pointer в RDX |
| Очистка до штатного завершения | `0x39E996` | `e865e40500` | Удалить per-frame запись до обычного RET |

В LIVE памяти FirstCall должен быть уже перехвачен EEex (ожидается `E9`), но это **ещё не проверено на Windows**. Исходная V120 доказала байты файла на диске, не текущие патчи процесса. Без проверки текущих байтов всех точек, а также атомарной установки нескольких JIT-хуков `HOLD`.

## Что уже сделано

- Сверены точные SHA полного пользовательского ZIP V120 и machine-code фрагмента `Hit()`.
- Python-тест проверяет допустимые участки и отсутствие пересечений, блокирует опасную прежнюю точку, отдельно тестирует умышленную порчу каждого фрагмента, принудительное включение JIT и замену исходного ZIP.
- Создана Lua-модель входа в `Hit()`, связи кадра со следующим сообщением и очистки. Сохраняет только строку RESREF и числа; `CItem` не удерживается после callback. Есть лимиты активных кадров и телеметрии.
- В Lua-файле **нет исполняемых JIT-патчей**; запуск `Start()` всегда запрещён до внедрения полноценной проверенной реализации. Ни один успешный тест не равен GAMEPLAY PASS.

## Что ещё требуется для одного безопасного игрового пилота

1. Исходный **Win64 callback wrapper**: сохранение volatile-регистров, XMM0–5, выравнивание стека, гарантия доступа к CItem при обоих исходах броска; source compile и runtime-load проверка.
2. Проверка EEex Lua binding `CItem.cResRef`, полномочий loader-label и наличия других патчей на трёх текущих адресах **в живом процессе**; запрет при несовпадении.
3. Устранение риска частичной установки трёх JIT-участков: failure atomicity / safe startup recovery. Без этого не разрешать даже «пассивный» игровой хук.
4. Обработка исключений и реентерабельности: очистка при normal return есть, при exception/unwind нет. Ограничение RAM и fail-closed.
5. Подтвердить тип `CMessage` и реальную видимую строку `combatLog` при промахе. Пока Lua записывает `journal_row=UNVERIFIED` и **не меняет строку**.
6. Только затем — отдельное осознанное разрешение на exact SHA guarded-install, внешняя резервная копия, last-only rollback, **один комплексный игровой тест**: меч/лук/праща/дротики/две руки/смена оружия/два атакующих/попадания/промахи.

**Важно:** текущая опубликованная версия общего обновлятора — V121. Новых игровых изменений и нового release нет.
