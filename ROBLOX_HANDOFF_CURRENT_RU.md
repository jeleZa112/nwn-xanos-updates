# НАЧАТЬ ЗДЕСЬ — ROBLOX_BG_AI
Обновлено: 2026-11-05.

Это продолжение долгосрочного проекта автопрокачки Roblox Zombie Rush Survival на Windows. Не начинать с нуля, не просить переприслать уже изученное.

## Читать в таком порядке
1. `ROBLOX_PROJECT_STATE_RU.md` — актуальные факты/текущая версия и блокеры.
2. `ROBLOX_PROJECT_LEDGER_RU.md` — решения, хронология.
3. `TRAINING_REVIEW_2026-11-05_RU.md` — разбор демонстрации и исправленная пользователем тактика.
4. `roblox_monitor.py` — реальный исходный код, публикация в ветке `roblox-bg-monitor`.

## Важнейшая задача сейчас
Бот должен **самостоятельно создавать лобби**, а не требовать, чтобы пользователь нажимал «Создать». Целевая конфигурация: «Пейзаж города», 1 игрок, сложность «Сложно». В программе пока только экспериментальная помощь с открытым меню и активным Roblox; автоматическое движение к площадке отсутствует. Не называть это завершённой автоматизацией.

## Тактика
Копить на первую пушку, строить группу на основной возвышенной позиции, при приближении зомби ставить защиту, при нехватке места выходить чуть дальше для дополнительных пушек и возвращаться. На 16-й волне пользователь специально вышел из защищённого места, чтобы проиграть — это НЕ доказательство провала стратегии.

## Обновление и изоляция
Пользователь запускает **один `ROBLOX_UPDATE.cmd`**; модель публикует новые версии в GitHub `jeleZa112/nwn-xanos-updates`, ветка `roblox-bg-monitor`. NWN (`main`) и BGXAI (`bg-eet-ai`) не трогать. После публикации указывать фактический коммит и честный статус проверки.

## План следующего рабочего шага
Исправить меню лобби, явно выбрать 1 игрока, правильную карту и сложность, валидировать состояние по кадрам, не нажимать при сомнении. Затем тестировать навигацию к площадке и фоновое управление без перехвата пользовательской мыши.

## Ограничения
ChatGPT не видит игру онлайн сам по себе. Изучение возможно по присланным логам/обучающим архивам. Захват в RAM проверен; независимое управление на фоне, создание матча, путь до базы и автоматическое строительство НЕ проверены.

- `roblox_monitor.py` в ветке `roblox-bg-monitor` обновлён до V1.7.0. Коммит `7cb3f5b33b632ee13c2a8584b86534047c36099f`. Сохранён старый единственный обновлятор `ROBLOX_UPDATE.cmd`, новые зависимости не добавлены.
- В код добавлены `KEYBDINPUT`, `SendInput` для физических scan-code событий, поддерживаемая Roblox комбинация `Backslash` (UI Selection), стрелка влево и `Enter`. После ОДНОЙ неудачной попытки мыши резервный метод пробует клавиатурную UI-навигацию с наблюдением кадров.
- Критический предохранитель: клавиша Enter **не отправляется**, пока CV-проверка не обнаружит однозначное новое синее/голубое выделение кнопки «1» относительно кадра до включения UI-навигации; 4 шага максимум; если выделение неоднозначно, не создаёт лобби и не тыкает вслепую. Текущий fallback только для этапа выбора количества игроков. Другая карта/сложность по-прежнему зависят от прежнего SendInput.
- Документы платформы: Roblox Default Bindings `https://github.com/Roblox/creator-docs/blob/main/content/en-us/includes/default-bindings.md`; Roblox Support `https://en.help.roblox.com/hc/en-us/articles/203314230-In-experience-Settings-and-Help` (UI Navigation Toggle). Поддержка функции платформой **не доказывает**, что конкретная игра позволяет фокусировать свои кнопки.
- Разработчик **не мог выполнить код в живом Roblox на пользовательском ПК**. Если кнопки не NavigationSelectable, фокус не будет подтверждён и клавиша Enter не отправится. Не выдавать V1.7.0 за готовый бот.

## 2026-11-05 19:11 — V1.8.0: оба backend-а мыши не сработали в Roblox
- По предоставленному `lobby(20261105-121207).log`: 19:11:30–31 `SendInput=1/1` при координатах (704,724), после этого `PLAYER_STATE_BEFORE_AFTER before=4 after=4`; 19:11:34 `LEGACY_MOUSE_TRACE target=(769,787) down_state=True`, после этого опять `before=4 after=4`; 19:11:37 `INPUT_BACKENDS_EXHAUSTED step=one`. Город распознан выбранным, 1 игрок не выбран. Кодовая версия V1.8.0 не обеспечивает цель.
- `GetAsyncKeyState(VK_LBUTTON)` подтверждает, что Windows видит состояние виртуальной кнопки, но НЕ означает, что Roblox / игровой UI обработал событие. Успешное `SendInput` аналогично.
- По документации Roblox `UserInputService:CreateVirtualInput()` предназначен для тестирования UI в контексте работающего experience, а не является доступным внешнему Python-скрипту универсальным API управления чужой игрой. Не представлять его как готовое решение.
- Аналогичный симптом обсуждался в Roblox Developer Forum: `https://devforum.roblox.com/t/unable-to-automate-keypresses-on-roblox/1944052`, где программный курсор движется без игрового клика. Это иллюстрация, не доказательство конкретной первопричины.
- ОСТАНОВИТЬ бесполезную цепочку версий, которые только переставляют курсор или меняют SendInput / mouse_event / PostMessage. Нет подтверждённого внешнего software-only пути ввода для этой пользовательской Roblox. Варианты для дальнейшей реальной реализации: аппаратный HID-ввод (требует отдельно совместимого устройства и проверки), либо собственная Roblox experience с внутренним API тестирования, но это не решает автоматизацию чужой игры. Не обещать готовую работу от недоказанного подхода.

## 2026-11-05 — аппаратный USB HID bridge V1.9.1
- После доказанной неудачи двух Windows-инъекций мыши (SendInput и mouse_event), сделан ДРУГОЙ физический путь: **Arduino Leonardo/Micro ATmega32U4**, которая распознаётся Windows как HID-мышь и USB COM.
- В GitHub опубликован реальный скетч: \`ROBLOX_HID_LEONARDO/ROBLOX_HID_LEONARDO.ino\` (коммит 7bbb33a19b6c5d8df079eab04bf79bc59cc39925), команды HELLO / ARM / MOVE / CLICK / DISARM, 5-секундный watchdog, ограничения скорости кликов, никаких клавиатурных событий.
- В одном основном \`roblox_monitor.py\` теперь интегрирован serial USB HID frontend (V1.9.0 commit 250be3423f848f3a594428a23b56a41acd64188f, V1.9.1 commit fdaeca66f8bb70caa0e7720854524f1e08dbd2d2). По умолчанию HID-режим, без Arduino — безопасное наблюдение без кликов. Автопоиск COM для известных VID Arduino, либо ROBLOX_HID_PORT=COMx; зависимость \`pyserial\`. Проверка подписи прошивки перед разрешением; относительные HID движения с визуальным контролем координат, CLICK только с открытым и сфокусированным Roblox, на каждой операции происходит DISARM и закрытие COM. В старый программный ввод самостоятельно НЕ откатывается; SOFTWARE — явный, не рекомендованный режим.
- Прошивка прошла локальную C++-проверку синтаксиса g++ с заглушками Arduino API; это НЕ реальная сборка ATmega32U4. Python хост фрагмент прошёл py_compile локально; весь основной файл на Windows не выполнялся. CI GitHub workflow \`.github/workflows/roblox-hid-check.yml\` создан (commit 67f70a199690a97b1251e9a453880db3fd58e108) для compile Python и сборки Leonardo; статус запуска пока не подтверждён.
- Русская инструкция \`ROBLOX_HID_SETUP_RU.md\` опубликована и обновлена (commit 93bae8fa11b6601f57c4310e5f3f1505254b1a93).
- **Нет физической платы/прошивки у пользователя по подтверждённым данным. Пользователь не получил тестированного рабочего бота.** Не обещать, что Roblox точно примет HID ввод; не требовать постоянных однообразных тестов. Единственный updater ROBLOX_UPDATE.cmd по-прежнему подтягивает основной Python файл из отдельной ветки, NWN main и BGXAI bg-eet-ai не трогать.
- Внешний USB HID сдвигает ОБЩИЙ системный курсор: не решает конечную потребность пользователя играть в фоне без вмешательства в мышь. Самостоятельный путь до площадки, строительство и бой остаются не реализованы.

## 2026-11-05 — V2.0.1 Windows Touch: новый путь без Arduino
- Пользователь подтвердил, что работает на ноутбуке без отдельной Arduino и просил ПРОДОЛЖИТЬ РАЗРАБОТКУ без покупки оборудования; прежний V1.9.2 HID-режим не применим. В основном файле `roblox_monitor.py` реализован `TOUCH` как backend по умолчанию, без pyserial/Arduino/COM, без UI Navigation/Backslash/WASD. GitHub commit `43e02a02d41d7c17d8a74654fbdf6764e5fb09cb`, startup API-preflight V2.0.1 `2cdf603b0414933ba57d291bde8aaad2ad68763f`.
- Новый метод применяет системные Win32 `InitializeTouchInjection/InjectTouchInput`, а не ещё один mouse_event. Определены структуры `POINTER_INFO` (96 байт x64) и `POINTER_TOUCH_INFO` (144 байта), тип PT_TOUCH, 0x10006 для down, 0x40000 для up; Windows API вызывается с `use_last_error=True`, журнал сохраняет WinError. Без поддержки API — явная ошибка, автоматического fallback к старой инъекции нет.
- Касание разрешено только при активном Roblox, если корректен прямоугольник окна и подтверждено меню. Максимум 1 касание на шаг, затем повторная проверка визуально выбранных city/one/hard; Create только при тройной проверке. После неудачи больше не тыкать, а сообщить `INPUT_UNCONFIRMED backend=TOUCH`.
- Модуль не двигает аппаратную мышь, но пока всё ещё требует foreground Roblox. РЕАЛЬНЫЙ Roblox НЕ проверялся, игра может игнорировать программный touch, а сами методы Windows API не гарантируют поддержку во всех средах.
- Русская инструкция: `ROBLOX_SOFTWARE_TOUCH_RU.md`, commit `202926a6812e83b61e24546bc4f8d8157977b679`. Добавлен отдельный ABI-тест `tests/test_touch_abi.py` (commit `e1e1be7f539a0febe71b7be166844bf1b7130cc6`), CI `.github/workflows/roblox-hid-check.yml` обновлён (commit `bfebfb8f01e2eaebb3847cc760bb1d992bdb704f`). Локально проверен аналогичный ctypes layout тест на x64: размер 96 и 144, без выполнения Windows API. Полный Python файл пока не удалось запустить в Windows среде разработчика, CI статус не подтверждён.
- Старые режимы `HID` и `SOFTWARE` оставлены только при явном выборе переменной `ROBLOX_INPUT_BACKEND`. Базовая задача автономного создания лобби ещё не доказана; путь к площадке, игра по волнам и независимый ввод в фоне не сделаны. Не выдавать V2.0.1 за полностью работающего бота.
