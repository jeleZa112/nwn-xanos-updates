## Правило № 0: запрещено начинать повторную работу без проверки предшественников

**Нельзя проектировать, писать, переустанавливать, заново тестировать или предлагать как новую функцию, пока не выяснено, что уже реализовано для этой же *цели и наблюдаемого поведения*, включая решения с другими названиями, номерами версий, в соседних чатах и смежных проектах.**

Проверка — обязанность ассистента, не пользователя. Фраза «этого раньше не было» без поиска по доступным источникам — недопустима. Отсутствие результата в одном handoff/чате не означает, что реализации нет. Если доказательств не хватает, писать «история проверена не полностью», а не «не реализовано». Не просить пользователя снова предоставить уже доступные логи, архивы, скриншоты или выполнить ранее пройденные тесты.

## Обязательный алгоритм перед работой (PRE-WORK GATE)

1. **Определить цель:** проект, требуемое наблюдаемое поведение/результат, конкретную подфункцию, рабочее окружение. Поиск вести по **смыслу функции и синонимам**, а не только по её новому имени/номеру. Не смешивать BGXAI, BG_EET_RU, BG Voice RU, EET, маркетплейсы и другие самостоятельные ветки.
2. **Прочитать актуальную точку:** действующий `00_READ_FIRST`/`PROJECT_STATE`/`HANDOFF`/`CURRENT`, реестр возможностей и известные отрицательные результаты, если доступен. Явно различить свежие данные и устаревшие исторические записи; последняя запись сама по себе не доказательство работы в игре.
3. **Сверить предыдущую реализацию:** искать связанный код, исходники, коммиты, патчи, версии, старые названия, предшествующие тесты/сохранённые логи и отчёты, архивы, методический реестр, доступные прошлые чаты. Проверить соседние ветви только если есть предметная связь. **Поиск ступенчатый:** сначала канонический индекс и текущие файлы → точечный поиск по функциональности в коде/архивах/логах → более широкая история только при расхождении. Не перечитывать всё подряд, если есть достаточные проверяемые сведения.
4. **Установить статус на основании фактов:** `NOT_FOUND_IN_CHECKED_SOURCES`, `PLANNED_ONLY`, `CODE_EXISTS`, `OFFLINE_TESTED`, `INSTALLED`, `LIVE_VERIFIED`, `FAILED`, `ROLLED_BACK`, `SUPERSEDED`, `UNKNOWN` или `HISTORY_INCOMPLETE`; при необходимости указывать отдельные CODE / TEST / DEPLOY / LIVE. Не считать лог, тест или саму запись о планах доказательством реального поведения. При противоречии предпочитать более позднее надёжное реальное свидетельство (установочный лог, хэш, игровой capture/скриншот) и документировать его область действия; не обнулять подтверждённые результаты старой формулировкой.
5. **Сопоставить новое требование с прежним результатом:** `ALREADY_DONE` — повтор запрещён; `PARTIALLY_DONE` — разрешено работать **только над доказанным пробелом**; `REGRESSION` — искать причину нарушения имеющегося решения; `NEW_REQUIREMENT` — делать минимальное расширение существующего пути; `HISTORY_INCOMPLETE` — сначала безопасно уточнять источники, без необоснованного нового деплоя/переписывания.
6. **Обосновать новое действие:** перед существенной разработкой иметь краткую запись «что уже было → подтверждение/ссылка → что именно отсутствует/сломалось → почему существующий способ не решает → минимальное следующее безопасное изменение/проверка». Если отсутствует хотя бы один существенный пункт, **не запускать новый цикл реализации по предположению**. Можно продолжать недеструктивный поиск и подготовку уточняющего аудита.
7. **Исполнить только дельту:** переиспользовать рабочие компоненты, существующий обновлятор, готовые инструменты, артефакты и проверенные тесты. Новую версию/программу/отчёт создавать только при реальной функциональной разнице, доказанной необходимости и отсутствии безопасного переиспользования. Не запускать повторные live-тесты без изменения значимого условия или нового подтверждаемого пробела.
8. **Зафиксировать итог в одном актуальном месте:** обновить `PROJECT_STATE`/`HANDOFF`/feature-реестр с идентификатором функции, найденными предшественниками, подтверждёнными стадиями, отсутствующей дельтой, точными ссылками на доказательства и следующим функциональным рубежом. Сохранять историю и отрицательные результаты, не плодить противоречащие «последние» файлы. При новых методах применить GLOBAL_METHOD_LEARNING_POLICY_V1.

Для каждой активной функциональной задачи вести или дополнять **одну** строку/запись в каноническом реестре возможностей проекта:

Существующий `PROJECT_STATE`, `HANDOFF`, JSON/реестр или однотипный журнал можно использовать вместо создания нового файла. **Один feature_id = одна функциональная цель**; версия меняет статус, а не порождает новую «задачу с нуля». Глобальная база методов не заменяет функциональный реестр: метод «как делать» и функция «что уже работает» — разные сущности.
